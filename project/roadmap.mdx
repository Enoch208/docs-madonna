The core testnet loop is working. The next milestones focus on broader verification, operational readiness, and carefully scoped integrations. This roadmap uses acceptance criteria rather than speculative release dates.

## Phase 1 — Prove the core loop

**Status: delivered on testnet.**

- Publish a product and merchant-funded campaign.
- Create a branching distribution graph with fixed parent links.
- Purchase with a client-generated order key and exact policy attribution.
- Verify buyer delivery, refunds, finalization, and claims.
- Expose receipts, six earnings buckets, canonical indexing, and public read access.
- Publish source verification and reproducible demonstration evidence.

**Evidence:** the [production journey and contract fixture](/project/proof).

## Phase 2 — Verify the strengthened experience and operations

**Status: continuing.**

Passkey-first onboarding preserves campaign context, and encrypted workspace sync includes conflict protection and backup restoration. The next priority is physical Chrome/Safari and cross-device PRF verification, then observed merchant-to-distributor usability tests. Expand operational checks around provider outages, replay, restore, capacity and monitoring.

**Exit criteria:** repeatable recovery exercises, documented alert ownership, meaningful load and gas measurements within the prototype limits, and reproducible user journeys across the supported wallet/device set.

The existing reorg recovery and transaction handling provide a foundation; broader operational testing is still required before stronger reliability claims.

## Phase 3 — Activate and verify optional integrations

**Status: implementation exists; activation and broader delivery remain.**

Aurora provider setup is enabled. Continue route-specific verification using authorized user-executed transfers through independently verified USDC delivery. Test route expiry and failure handling. Preserve the separation between mainnet funding and testnet settlement.

For developer access, SDK 0.1.3 is published on npm as `@enochid/spoke-sdk`, with a matching GitHub release archive, tested installation, ESM/CommonJS builds, declarations, examples and compatibility guidance. Initial SDK distribution is complete. Define any future write SDK around explicit user signing and idempotency. Improve insight coverage without letting external history determine payout eligibility.

**Exit criteria:** real integration evidence, supported configurations, published integration instructions, and accurate availability labels.

## Phase 4 — Extend distribution workflows

**Status: core partnership workflows shipped; extensions remain designed.**

Invitations, partner discovery/comparison, Partner Passport, live Network Activity and bounded Partner Intelligence are shipped. Validate adoption and usability before extending communities, merchant growth tools, teams, API keys, webhooks and commerce connectors. Move each feature from Demo to live only when its backend, permissions, failure handling, and end-to-end journey are complete.

**Exit criteria:** tested live behavior and an updated method registry for each shipped feature. A finished screen alone does not satisfy this milestone.

## Phase 5 — Prepare mainnet settlement

**Status: future release gate.**

Mainnet commerce requires an independent security review, remediation and verification, reviewed token and deployment configuration, gas/capacity analysis, operational readiness, and explicit release approval. The current freely mintable SDUSD deployment is not a mainnet payment system.

**Exit criteria:** published scope and limitations, verified deployment artifacts, tested recovery and monitoring, and an explicit announcement of supported mainnet functionality.

## How progress is reported

Update [current status](/project/status) when functionality is actually deployed and verified. Attach source, transaction, or test evidence where possible. Keep future work in this roadmap and keep sample activity labeled as sample activity.

## Workstream acceptance matrix

The roles below describe ownership needed for each workstream; they are not assignments to named people or commitments to release dates.

| Workstream             | Role needed                               | Acceptance evidence                                                                                                      | Dependency                                       |
| ---------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| Wallet and recovery UX | Frontend and wallet integration           | Recorded supported-device sign-in, recovery, cancellation, and resume journeys                                           | Defined supported wallet/device matrix           |
| Product delivery       | Application and security                  | Private asset ownership, refund revocation, grant expiry, and restore tests                                              | Reliable persistent file storage                 |
| Indexing operations    | Backend and infrastructure                | Provider-failure drill, canonical replay, measured catch-up, alerts and restore evidence                                 | Independent RPC capacity and durable checkpoints |
| Aurora activation      | Integration owner and transfer authorizer | User-executed source transfer, verified canonical USDC receipt, expiry/failure handling                                  | Provider application configuration               |
| SDK distribution       | Developer tooling                         | Complete: npm package and matching GitHub archive, isolated installation, versioned examples and live API reads verified | Stable intended public method set                |
| Live extensions        | Product and implementation owners         | Backend permissions, failure paths, end-to-end proof, and updated method availability                                    | Validated scope for each workflow                |
| Mainnet settlement     | Contract/security and operations          | Independent review, remediation, capacity analysis, verified deployment, readiness sign-off                              | Completion of release gates                      |

## Known limitations to close explicitly

The `reversed` earnings bucket exists in the shared contract but remains zero in the current live earnings projection; the settlement contract does not expose post-finalization reversal. Product `accessTiming` is modeled, but the current entitlement service accepts pending/finalized purchases and does not establish a separate after-hold access enforcement mode. The prototype also restricts one node and one purchase per wallet per campaign.

Future releases should either implement additional behavior with complete tests or narrow the exposed contract and copy through a reviewed compatibility change. Documentation must not fill an implementation gap with a promise.
